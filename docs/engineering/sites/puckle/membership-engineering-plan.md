# Puckle membership — final engineering implementation plan

**Status:** Documentation only; complete proposal for final implementation approval.  
**Revised:** 14 November 2026.  
**Source of truth:** [Membership design specification](../../../design/sites/puckle/membership-spec.md).  
**Scope:** Shared account security/safeguarding/explicit permissions, minimum public-publishing enforcement, Puckle profiles and public Join/contact journeys, independent tuition enquiries, parental-approval records/email, one isolated client onboarding host, selected-account backfill and verification.

## 1. Decisions, reuse and strict scope

Puckle, Switchplay and Strat17 share ordinary users and authentication. Keep credentials/account IDs in users, optional authoritative safeguarding facts on that account, and Puckle education/category/contact/onboarding information in puckleMemberships. There is no parallel account system or generic multisite profile framework.

New email-based student/teacher registration proves email ownership before account creation and automatically establishes the normal session afterwards. Mobile is visible immediately on all Join categories and optional with email. Student/teacher no-email mode creates only a mobile contact request for founder follow-up; interest submissions are always contacts. No SMS authentication or phone login.

One parental approval covers equivalent Group Learning across all three websites under the accepted common scope/explanation. Approval is not permission for live tuition. The project records/exposes facts and performs no Group Experience enforcement. No active group implementation is needed to complete membership work.

Remove all previous provisional memberships, enquiry-linked claims/invitations, issuer endpoints, account activation pages/tokens and public existing-account linking. Email challenges and approval/reset action capabilities are purpose-specific security records, not membership activation machinery. Future personal/admin membership invitations, reusable admin onboarding and manual account arrangements for no-email contacts are separate work. seed:user stays unchanged.

Reuse the existing account/session implementation, MongoDB connection/transaction guards, Puckle public layouts/CSS modules/phone input, existing tuition form/endpoint/collection and test infrastructure. Do not redesign My Decks, Creator/Library, CardData/DeckData, progress/confidence/reflections, media, Step Visuals, groups, navigation, gestures or global CSS. The newly agreed exception is minimum server enforcement and existing error feedback at actual public-publication boundaries. New self-registered students/teachers can create/publish privately immediately but cannot publish publicly until the founder grants users.permissions.publicPublishing directly in MongoDB. Neither teacher category nor parental approval grants this permission. Initialising existing empty personal arrays on a new account is required compatibility, not a learning-data change.

## 3. Authoritative data model and preparation

### 3.1 Shared users and safeguarding

users keeps its identity/credential/account fields and existing learning data. Add optional emailVerifiedAt, sessionVersion (missing means zero), passwordChangedAt, and safeguarding. Do not expose these through the existing AuthUser/JWT projection except the internal session-version claim. Declare optional publicPublishingRevision for the transactional publication guard described in section 3.5. New account insert initialises decksData: [], cardsData: [] and existing empty compatibility sharedDeckData: [], with isAdmin false and permissions: { publicPublishing: false }. UserDocument must type cardsData consistently with existing learning records rather than copying the outdated seed script. Both membershipDTO in cards/readModels.ts and assertUser in cards/repository.ts reject a missing cardsData or decksData array with NEW_MODEL_USER_REQUIRED. Existing learning shapes/types are unchanged.

| Optional shared safeguarding field | Meaning/invariant |
| --- | --- |
| dateOfBirth | Strict YYYY-MM-DD date-only or absent. The sole account-authoritative DOB. Never an authoritative age counter. |
| dobSource / dobRecordedAt | Source self-declared or operator-entered, separate from verification; absence represents unknown history. New student input is self-declared; backfill must not invent a declaration. |
| ageAssurance | verification: none or independent, plus method, verifiedAt and justified evidenceReference when independently verified. A source/recorded date alone is never verification. Public forms can only produce verification none; guardian email/declaration cannot set independent. |
| dateOfBirthHistory | Reviewed old/new values, reason, actor, time and relationship to invalidated assurance. Never transfer verification tied to an old DOB to a new DOB. |
| groupExperienceApproval | One common activity-scope record: scopeId, accepted explanationVersion/scope snapshot, status, guardian contact/declaration evidence, request/decision/withdrawal timestamps and history (actor, event kind and reason distinguish guardian withdrawal from reviewed operator revocation). Both end the current approval as withdrawn without erasing accepted evidence. Applies to equivalent Group Learning on Puckle, Switchplay and Strat17. |

Use one concrete common scope identifier, for example shared-group-experiences, with a versioned explanation describing the three sites and actual visibility/sharing conditions. The sending site's ID is provenance/branding, never a per-site approval key. Do not add puckleApproved/switchplayApproved/strat17Approved or require a maths profile to read shared facts. Materially expanded/divergent activity may require a later additional approval; do not implement that future activity or automatically broaden consent now.

Absent DOB is unknown, not adult. Email ownership and guardian declaration are not independent age verification. Do not build a verification-provider workflow or store identity documents; allow relevant evidence references for authorised future use.

Use Europe/Dublin calendar dates for age and UTC timestamps for events. A 29 February birthday is reached on 1 March in a non-leap year, subject to required legal correction. Inject today/clock into pure functions. Parse DOB strictly rather than using dateOnly.ts's fallback-to-today helpers. New Puckle student forms enforce >=13, not global account validation. Historical/backfilled partial data can remain unknown.

New src/lib/userSafeguarding.ts exposes a server-only getSafeguardingFacts(userId, today) and targeted correction/approval writes. It returns raw age/assurance/common-scope evidence, not canJoinGroups or permission decisions. Authorised code from any site can call it without loading puckleMemberships. Own-data endpoints derive user ID from current authentication; never add public arbitrary-user fact lookup.

Retain separate puckleJoinContactRequests and puckleInterestContacts collections. Their validators, optional student DOB, notification purpose and communication permissions already differ; merging would require a discriminated contact schema without removing a persistence flow. Shared notification/retrieval helpers suffice. This rejects the optional merge for the MVP without creating an account system.

A no-email contact's submitted DOB is submission history about an unlinked contact, not a duplicate authoritative user DOB. No automatic conversion or sync is built. Future manual onboarding is separate work and must establish the intended person's facts/credentials afresh.

For new Puckle profiles, original registration source is join; optional context may record that the visitor came from tuition success, without pretending the enquiry created membership. Reserve admin-script/invitation as future source values only. New student profiles mark welcome eligible with seenAt unset. Teachers do not receive a student free-maths-session welcome. Known-account backfill defaults welcome eligible false; appropriate approval reminders can still apply without inventing a past/new registration event.

### 3.3 Approved indexes and preparation

Create explicit unique indexes on existing users.email and users.username; normalise new email trim/lowercase as current login does, preserve binary/exact username case sensitivity, and do not add provider-specific email alias rules. Existing users have been confirmed duplicate-free. Inspect current definitions and expected normalisation; report unexpected failures without renaming, merging or cleaning accounts.

puckleMemberships has a unique required userId index. Contact/tuition mobile/guardian fields are not globally unique. Add only needed date/relationship/notification lookups. Challenges/actions have unique random proof digests/IDs and cleanup indexes; expiresAt controls capability validity, while any separately reviewed cleanupAt permits only the necessary expired-link renewal lookup, never an expired approval/reset action; rate windows expire independently. Enforce expiresAt in each operation, not by waiting for TTL cleanup. Never TTL-delete users, profiles or safeguarding history.

Use explicit, idempotent scripts/prepare-puckle-membership.ts with existing applicationDatabase/Mongo helpers. Precreate collections and indexes, particularly puckleMemberships, before transactional traffic. Confirm transactions in the target Atlas deployment; the repository restricts application traffic to Atlas and the existing helper uses snapshot/majority withTransaction, but mongodb+srv alone is not a general guarantee of transaction support. No index creation at import/public request time. One-time known-account population belongs to phase 7, not a broad legacy cleanup/migration.

### 3.4 Targeted writes and race invariants

Account creation + Puckle profile + verified proof consumption commit in one existing Mongo transaction. Generate the ObjectId, hash new credentials and prepare the signed version-zero session token before retried transaction callbacks. If signing/configuration fails, create nothing. Reuse the prepared ID/token across transaction retries; write the cookie only after successful commit. Send external email after persistence, never inside a retried callback. Handle duplicate key 11000 explicitly: Mongo transaction retries do not turn it into a successful registration. Roll back account/profile/proof together and map known indexes to editable username or neutral email outcomes, leaving otherwise valid proof reusable. Unique indexes settle concurrent account races; code/proof ownership never signs into or overwrites an existing colliding account.

Corrections/approvals/backfill use narrow $set/$push/$setOnInsert and state/version preconditions. Never replace users or normalise learning arrays. Append evidence only when a fact changes; repeated identical backfill is a no-op. Tests must interleave a learning-data write with a safeguarding write and preserve both.

### 3.5 Explicit shared permissions and actual publication boundaries

Every account must have users.permissions: { publicPublishing: boolean }. This is the initial explicit grant record, not a list duplicating every ordinary capability. Ownership, private learning/authoring/publication and existing validation remain ordinary capabilities. isAdmin, teacher category, DOB and guardian approval are separate facts and never substitute for publicPublishing. Missing/malformed permissions deny public publication even during preparation. New accounts always write false; no signup payload may set it.

The founder changes only the reviewed account's boolean directly in MongoDB. Example mongosh operations (documentation only; not run):

```javascript
// Resolve/review this exact account first, then grant. matchedCount must be 1.
db.users.updateOne(
  { _id: ObjectId("REVIEWED_ACCOUNT_ID") },
  { $set: { "permissions.publicPublishing": true } }
)
// Revoke: same exact filter, $set { "permissions.publicPublishing": false }.
// Do not replace the user/permissions document, change isAdmin, or edit content.
```

Use a new small server-only src/lib/userPermissions.ts. The decision reads the current database grant, not an AuthUser/JWT claim or a cached UI value. For an actual public write, conditionally update the actor's users record with filter permissions.publicPublishing: true and $inc publicPublishingRevision: 1 in the same publication transaction. This small internal counter is a write-conflict guard, not a permission value or age counter: it serialises publication with a founder's direct flag update. A plain snapshot read alone would permit a concurrent revoked snapshot to commit. An unmatched grant uses the existing CardArchitectureError/requireCondition with PUBLIC_PUBLISHING_FORBIDDEN, so existing HTTP error mapping applies; retried transactions recheck. Put the guard before the version insert without reordering existing reference locks/validation. Preserve other user fields. Match the existing repository actor-to-_id conversion (ObjectId in real accounts, string IDs in disposable fixtures). No permission-management API, admin screen, grant request workflow or session refresh requirement.

| Actual boundary / existing route coverage | Required behaviour |
| --- | --- |
| CardRepository.publishCard; PATCH /api/card-templates/[cardTemplateId] with type publish | Guard effective visibility public before inserting a new CardVersion, including subsequent versions of already-public Cards. Private versions succeed without the grant. |
| CardRepository.publishDeckInSession; POST /api/deck-templates/[deckTemplateId]/publish | Same check before a new public DeckVersion; shared internal boundary covers explicit publishing and callers below. GET publication review is read-only. |
| CardRepository.copyOwnedCard; POST /api/card-templates/[cardTemplateId]/copy-to | A clean destination Deck can auto-publish via publishDeckInSession. If public and unapproved, reject the whole atomic Copy with 403 and no partial append/reference/receipt changes. Private destination Copy and ordinary private draft paths retain their current behaviour. Do not silently downgrade a permanent-public Deck or redesign Copy. |
| InfoCardRepository.publish; POST /api/info-cards/[infoCardId]/publish | Guard root.draftVisibility public in the transaction before inserting a new InfoPublication, including updates to public Info Cards. Private publication remains allowed. |

Creation/save/fork/promotion operations inspected in cards/repository.ts only stage drafts/visibility; they do not insert public versions and need no redundant permission gate. Fork results start private even if public intent is staged. Public-facing discovery reads published visibility, not draftVisibility. Test these properties to detect any missed path. New-public checks also apply to multi-item publication through the same methods. Recovery that only returns an already-committed receipt is permitted without a fresh grant because it creates no publication; tests must prove there is no new write.

Return 403 PUBLIC_PUBLISHING_FORBIDDEN through existing cards/http.ts mapping (codes containing FORBIDDEN already map to 403); Info Card routes use that same boundary. The two existing message helpers and Copy's existing feedback explain: public publishing requires approval, private work/edits remain available. Do not hide all Publish buttons: private publication is used by personal learning. A staged public draft can be switched back to private under existing rules; an already-public root cannot, and remains saved without further publication until approved. Revocation preserves all existing public versions and private learning data.

Before production enforcement, phase 7 reviews a permission-only disposition for **every existing shared account**. Grant true only to founder-confirmed trusted account IDs; false to explicitly reviewed others. Do not infer trust solely from age of account, email, published content or isAdmin. Combine this with optional selected Puckle/safeguarding additions without forcing a Puckle profile on every user. Review unresolved accounts before enabling the guard, never grant all old accounts true or silently interrupt trusted users. No extra trust moderation, media restrictions or Chromium quotas are included.

## 4. Shared account security, email and contact validation

### 4.1 Email ownership and final registration

The new Puckle registration form first collects details and requests a code for its normalised email. Keep password only in live form memory; never put it into sessionStorage, analytics, challenge records or logs. Requesting a code creates no user/profile and reserves neither email nor username.

Use a random six-digit code with ten-minute expiry, a protected keyed digest, random flow/challenge binding and at most five failed attempts per challenge. Check attempts atomically, including concurrent guesses. Resend after approximately 60 seconds rotates the code/generation and invalidates the prior one. Changing email invalidates the old form proof. For syntactically valid requests use neutral wording such as “Check your email for the next step”; known-account email receives sign-in/reset guidance instead of a registration code. Avoid a distinguishable account-existence status/body or challenge-handle shape; an opaque handle for an existing email must never become a registration proof. Rate-limit that guidance too. Provider failure uses a neutral retry response without exposing whether the account exists; do not assert successful delivery.

Final POST /api/public/puckle/membership validates the live full category payload and matching unexpired proof. Verify email, check Puckle-specific fields and consume the proof atomically with account/profile creation. No separate registration activation page/token or stored incomplete authenticated user. If a uniqueness race wins elsewhere, return an editable username conflict or neutral email/sign-in/recovery guidance without account mutation or implicit existing-account sign-in. On transaction rollback retain otherwise valid email proof until its original expiry; changing only username does not require another code. Do not add a username-availability endpoint.

Pre-generate the account ID, hash and signed normal session before the transaction (section 3.4). After commit, set that prepared session before success and perform ordinary full-document navigation to /decks. No registration hint/local-storage hand-off is needed: the server knows welcomeEligible and seenAt, and the host remounts on document entry. Fresh entry avoids a stale unauthenticated RSC/root result. If cookie delivery fails after commit, offer ordinary login/recovery rather than retrying account creation as a new person.

### 4.2 Credentials and recovery

prepareAccountCredentials in auth.ts handles core input only: username 3–30 ASCII letters/digits/_/-, exact case and trimmed boundaries; email trim/lowercase; new passwords at least 12 Unicode characters and <=72 UTF-8 bytes, without trimming/composition rules or silent truncation; bcrypt cost 12. insertAccount writes the ordinary user with required empty cardsData/decksData and permissions.publicPublishing false in the supplied Db/ClientSession; prepareSession/writePreparedSessionCookie separate signing from post-commit cookie delivery. Student DOB/course/null-level validation stays in Puckle registration code. Existing login accepts existing credentials exactly as before, even if they do not satisfy new registration rules.

Shared /login/forgot-password is a normal request page under the reserved login route. The reset interaction itself is in the isolated action document, not a separate analytics-loaded React page. New POST /api/auth/password-reset/request returns a neutral result and sends a 30-minute single-use link to the stored account email. Legacy accounts without emailVerifiedAt remain eligible for their existing email-based recovery; they are not forced through new registration. If that address is wrong/unavailable, use reviewed support, never automatic identity reassignment.

Reset completion verifies the account-bound in-memory token, new password and unused proof, then atomically changes only passwordHash, passwordChangedAt and sessionVersion, consumes the reset proof and invalidates any other outstanding reset for that account. It preserves account ID/email/username and learning data, offers ordinary sign-in and publishes auth invalidation. Do not automatically sign a browser into the reset target or log out an unrelated currently signed-in account merely because a parent opened a child link.

### 4.3 Backward-compatible session security and the login race

Add optional users.sessionVersion, default zero. Newly issued JWTs contain the version; legacy tokens with no version are zero. getCurrentUser checks the signed version against the current account. A reset increments the version; old sessions fail without affecting users who have not reset. Preserve cookie name, HTTP-only/secure/sameSite/path flags and 30-day duration. Keep AuthUser and /api/auth/me/login response fields unchanged. No DOB or approval facts go into JWTs.

The version used for login must be captured with the account/password snapshot that passed bcrypt verification. Reading a fresh version only later in setSession could let old credentials racing a reset receive a new valid version. Recommended narrow implementation: add signInWithPassword in auth.ts using a private credential loader, carry its checked version into session signing, and adapt the existing login handler to use that helper while returning the same { user } response. Keep authenticateUser's exported core result/behaviour for compatibility and setSession's current callers supported. The internal checked session version need not become an enumerable AuthUser field. Onboarding requires current identity/status, not an expiry timer.

The latest request explicitly approves this narrow login-handler edit. A token prepared from the old password snapshot carries the old version and is rejected after reset, even if cookie delivery follows the reset. Do not fresh-read the new version to stamp that old proof, hide metadata in AuthUser or introduce a credential cache. Existing login error/JSON/cookie behaviour remains unchanged.

### 4.4 Mobile, no-email and interest validation

All Join category views render PublicPhoneInput immediately and show Don't have an email address? below email. Reuse existing E.164 formatting, limits and form error/focus patterns without modifying the phone component. A supplied mobile must be valid even when optional; it is not verified or unique identity.

Email mode student/teacher requires email proof and credentials; mobile is nullable. No-email mode requires email absent/mobile present and omits username/password entirely. Clear credential state when switching, never persist it in a draft, and server-reject credential fields on contact-only payloads without logging their contents. Student contact requests still validate name, DOB >=13, course and applicable level; teacher contact requests require name/mobile with optional introduction and no mandatory DOB. Confirm contact follow-up, not registration/account access. Do not automatically convert requests later.

Interest always needs name, reason and email or mobile, with optional message. Its immediately visible mobile and no-email route have the same contact checks. An unchecked optional email-updates checkbox records explicit choice/version/time; phone-only disables email updates with a clear explanation and stores false/not-applicable. No promotional-SMS opt-in/sender is built. Relevant requested personal follow-up remains possible without an updates opt-in.

### 4.5 Shared email and founder notifications

New src/lib/siteEmail.ts is one concrete provider adapter with trusted per-site sender/origin settings. Shared recovery/security templates in src/lib/accountEmailTemplates.ts use the requesting site's trusted branding/sender configuration; Puckle-only Join/founder copy lives in its own memberEmailTemplates.ts. The common approval disclosure is shared versioned data. Do not import a Puckle public component/template into global authentication merely to send password recovery on another site. No service registry, queue, notification platform or campaign engine. Missing provider/sender configuration is reported, not silently replaced by a different site's identity. Never derive email action destinations from arbitrary Host/redirect input.

Persist pending notification status atomically with the tuition/teacher-profile/no-email/interest save. From the submitting Route Handler, register after() from next/server only after successful persistence/transaction commit, then return the successful response without awaiting founder email. The callback uses the stable source collection/record ID, sends via siteEmail and records sent/failed/unknown with sanitised references; catch errors inside it. Notifying on all interest contacts is the simplest low-volume choice and uses this same utility. Notification failure never changes saved submission/registration success. Store pending/sent/failed/unknown, timestamp and sanitised provider/error reference beside the source record. A crash after commit can leave pending, and a timeout may be unknown; do not claim delivery or roll back a saved enquiry.
